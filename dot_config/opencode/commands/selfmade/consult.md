# 技術諮詢

**待決策問題**: $ARGUMENTS

若為空，以當前對話中最近一個尚未決定的技術選型或架構問題為準；仍無法判定時，直接詢問使用者要決定什麼。

本命令只做決策諮詢，不修改檔案、不開始實作。

## 1. 先建立決策脈絡

1. 讀取與問題直接相關的程式碼、設定、相依套件版本與專案說明，找出既有技術棧、慣例與限制。
2. 涉及函式庫、框架或雲端服務的 API、版本或行為時，使用 `find-docs` 查證，不依賴記憶。
3. 整理出：
   - **決策**：這次要選的到底是什麼（一句話）。
   - **硬性限制**：不可違反的條件，例如既有架構、相容性、授權、部署環境。
   - **取捨偏好**：時程、維護成本、效能、擴展性中何者優先。
4. 若缺少的資訊會改變推薦結果（例如規模、時程、團隊熟悉度），先提問，最多 3 題；不會改變結果的缺口，改寫成明確假設繼續。

## 2. 產生方案

以「維持現狀或最小改動」作為比較基準，再提出方案：

- ⚡ **快速方案**：最少改動、最快上線，接受已知限制。
- 🛡️ **穩健方案**：在目前限制下取得平衡。
- 🌟 **理想方案**：以長期演進為優先，接受較高初期成本。

規則：

- 每個方案必須實際可行，並符合全部硬性限制。只有一或兩個可行方案時，如實說明原因，不得為湊滿三個而編造。
- 推薦不預設為穩健方案；依證據與取捨偏好選擇。
- 規模估計使用相對等級 `S / M / L / XL`，並寫出依據（例如受影響的檔案、模組或整合點數量）。不得編造天數或工時。
- 區分已查證的事實與推論；推論需標示。

## 3. 回報格式

先給結論，再給細節：

```markdown
## 推薦：<方案名稱>

<一到兩句：為什麼在這個專案的限制下它最合適>

**決策**：<一句話>
**假設**：<影響結論的假設；沒有則寫「無」>

## 方案比較

| 面向 | 維持現狀 | ⚡ 快速 | 🛡️ 穩健 | 🌟 理想 |
|------|----------|---------|---------|---------|
| 核心做法 | | | | |
| 規模（S/M/L/XL） | | | | |
| 主要風險 | | | | |
| 可反轉性 | | | | |
| 維護負擔 | | | | |

## 各方案重點

### ⚡ 快速方案：<名稱>
- 適合：<情境>
- 代價：<放棄了什麼>
- 證據：<file:line、文件連結或版本>

（穩健、理想方案同格式）
```

## 禁止事項

- 不得在未讀取相關程式碼或設定前就給出推薦。
- 不得編造工時、效能數字、基準測試或版本資訊。
- 不得在本命令中修改檔案或開始實作；使用者決定方案後，另行下達實作指示。
